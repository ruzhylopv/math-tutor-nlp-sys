# Roadmap: milestones M1-M7 (approved 2026-10-25)

Status: approved by the developer in the PR review. Each milestone still needs its own plan, approved in chat before
any code (CLAUDE.md, workflow rule 1), saved under `docs/plans/nodes/` or `docs/plans/design/`.
Design reference: `docs/architecture.md` and `docs/plans/design/2026-10-25-tutor-state-outline.md`.

## How every milestone runs
1. A plan for the milestone, approved in chat.
2. A stack of small PRs, one concern per layer (models, then tools, then node and tests, then eval script and
   dataset), opened with `open-pr` and the `gh-stack` skill.
3. The review loop on each PR (2 passes), then the developer's review. Requested changes go through
   `address-review`.
4. A CRISP-DM entry with the dev-split metrics in `docs/crisp_dm_log.md`, and the decisions with rejected
   alternatives in `docs/decisions.md`.
5. The test split is used once, in M7, for the final reported numbers.

Definition of done per node (CLAUDE.md): follows the node contract, unit tests pass without network, an eval
script writes a metrics file to `evals/results/<component>/`, a CRISP-DM entry exists, committed.

## Order and parallelism
- M1 first: it gives a runnable end-to-end skeleton.
- M2 and M3 are independent, so data preparation for one can run while the other is built.
- M4 needs M2 (verdicts) and M3 (structured steps). M5 needs M4. M6 needs M1-M5. M7 is last.

## Where the open items get settled
| Open item | Milestone |
|---|---|
| Model name; whether `finish_diagnosis` needs an eval (CLAUDE.md exemption) | M1 |
| What counts as a valid step; substitute / check steps; restricted parser; the single predicate | M2 |
| Target grades; where `parse_input` sits; `final_answer_only` path | M3 |
| Error-type taxonomy and its fallback value; Eedi coverage and mapping to our query | M4 |
| Counterexample tool design; leakage-check inputs; canned fallback hints; hint cap | M5 |
| Reset points and stale fields; `stage` initialisation; checkpointer; scenario YAML; practice threshold and wording | M6 |

## Risks
- Free OpenRouter models: weak structured output and rate limits. Checked early, in M1 and M3.
- Eedi may not match the retrieval query or contain the demo's misconceptions. Checked at the start of M4;
  fallback is a small hand-made supplement.
- The hand-made labels depend on the developer's time. Requested at the start of M2.
- Time: the milestones are ordered so that M1-M4 already give a working diagnosis pipeline if M5-M7 slip.
