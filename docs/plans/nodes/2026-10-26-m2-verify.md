# Plan: M2 `verify` (approved 2026-10-26)

Goal: the deterministic core of diagnosis. `verify` checks the final answer and each step with SymPy and
returns `is_correct` and `step_verdicts`. No LLM. Data for its unit tests and eval is mined from MATH and
PRM800K plus agent-made negatives. Roadmap: `docs/plans/design/2026-10-25-roadmap.md`.

## Decisions (from the developer)
- Task types in scope: solve, simplify, expand and factor. So `verify` handles expression chains (equivalent
  as expressions) and equation chains (solution sets).
- Positives (`equivalent` steps) are mined from MATH solutions.
- Wrong steps are produced by the agent. This is an explicit exception to the `run-eval` skill's "do not
  create labels yourself": every case carries its provenance (rule and seed), the label comes from the rule
  that produced it and not from SymPy, a numeric check discards a corruption that is secretly still
  equivalent, and the developer spot-checks a sample (about 20 percent).
- SymPy only. No LLM-only localization variant and no ablation.

## Decisions (proposed by the agent, approved)
- **Linear chains only.** Each line is compared with the previous line of the same chain. A solution with
  sub-computations is split into separate chains (each `align*` block or blank-line-separated block).
  Known limitation: a student who computes two sub-products and then combines them gets a false
  `not_valid` on the line that does not follow the previous one. Recorded as open.
- **Valid-step rules** (relation of a line to the previous line):
  - expression to expression: `equivalent` if the difference simplifies to zero;
  - equation to equation: `equivalent` if the solution sets are equal, `implies` if the new set contains the
    old one, otherwise `not_valid` (losing a solution is `not_valid`);
  - a closed statement without variables is valid if it is true (`equivalent`), `not_valid` if false;
  - input that cannot be parsed is `unparsable`;
  - a line that narrows the solution set is valid only when it equals the original problem's true solution
    set (rejecting an extraneous root), under a new relation `narrows`. This adds `narrows` to the `Relation`
    literal and to `is_clean_solution`; the tests that pin the literal values change on purpose.
- **Final-answer data:** PRM800K records with a model answer and the ground truth. Candidate labels come
  from PRM800K's own grader (`grade_answer`); our SymPy check is run as well and the developer adjudicates
  only the disagreements, which keeps the labels independent of SymPy.

## Findings of the data pre-step (2026-10-26; test files only, nothing committed)
- PRM800K (MIT; no separate data licence stated; data files in Git LFS): `phase2_train` 435 MB,
  `phase2_test` 12 MB, `phase1_train` 8 MB, `phase1_test` 1 MB, `math_splits/train` 10.4 MB, `math_splits/test`
  0.4 MB. The labelers' instruction PDFs could not be read here (no PDF renderer), so the meaning of the ratings
  comes from the README and the data.
- `math_splits/*.jsonl` carry `subject`, `level` (an integer 1-5), `answer`, `solution` and `unique_id`, so
  records join to MATH metadata by problem text. All 2762 `phase2_test` records joined.
- `phase2_test`: 2762 records over 458 problems; `finish_reason` found_error 2077, solution 587, give_up 98;
  completion ratings +1 18174, 0 2002, -1 6080, null 966; every record has `pre_generated_answer`.
- Algebra levels 1-3 in `phase2_test`: 369 records over 63 problems; found_error 221, solution 144, give_up 4;
  of the 144 finished solutions 130 string-match the ground truth and 14 differ (crude comparison);
  576 completions rated -1, 327 of them containing "=". The sampled -1 steps are real model algebra slips
  (for example `4x-1=x+3` after subtracting x from one side only), written as sentences with embedded LaTeX.
- MATH (MIT): the Hugging Face copy `qwedsacf/competition_math` has 12.5k rows in one `train` split with the
  columns `problem`, `level` ("Level 1" to "Level 5"), `type` (7 subjects) and `solution`; it is a mirror, not the
  official release.
- `sympy.parsing.latex.parse_latex` needs the `antlr4` package, which is not installed. Plain-text steps parse
  with `parse_expr` and implicit multiplication.

## Stack
0. `chore/m2-plan`: this plan, the decisions and the CRISP-DM entry.
1. `feat/relation-narrows`: add `narrows` to `Relation`, `VALID_RELATIONS` and their tests.
2. `feat/verify-tools`: the restricted parser, the relation checker (expressions, equations, closed statements,
   `narrows`) and the answer check in `src/tutor/tools/`, with unit tests on hand-built cases.
3. `feat/verify-data`: the builders (MATH chain miner with a LaTeX-to-plain-text converter, the corruption
   generator, hand-written `implies` and `unparsable` cases, the PRM800K answer extractor), the fixed dev/test
   split by problem, and the datasets. Raw downloads stay outside the repo (size, licences); scripts take a path.
4. `feat/verify-node`: the real `verify` node, the eval script and its metrics file, and the CRISP-DM entry.

## Proposed dataset format (for review before layer 3)
- `evals/datasets/<split>/verify_steps.jsonl`: `id`, `task_type` (solve | simplify | expand | factor), `problem`,
  `prev`, `curr`, `relation`, `source` (math | generated | handwritten), `provenance`.
- `evals/datasets/<split>/verify_answers.jsonl`: `id`, `problem`, `answer`, `ground_truth`, `is_correct`, `source`.
- Split by source problem with a fixed seed, so no problem appears in both dev and test.

## Metrics
Step-verdict accuracy and a per-relation confusion table; answer-check accuracy.

## Out of scope
Branching solutions, an LLM-only variant, inequalities, and the taxonomy (M4).

## Open
- The restricted parser's grammar, the number domain (reals assumed), and the handling of plus-or-minus and
  square roots.
- Whether to download the 435 MB `phase2_train` file for more answer data (decided when layer 3 starts).
